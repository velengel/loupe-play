# 実装前理解確認ゲート

StoryとADRが揃っていても、実装の前提が揃ったとは限らない。たとえば「同じ曲」の意味をpathと考えるか、恒久Track identityと考えるかで、正しいtestは逆になる。ずれを見つける場所は、testを書いた後では遅い。

このゲートは、重要な判断だけをRED testの手前で止める。利用者を試験するためではない。Codexが判断材料を説明し、利用者の説明から前提の一致を確かめるために使う。

## 適用判定

次のどれかが変わるStoryは`Required`とする。

- ドメイン概念、用語の意味、利用者に見える状態遷移
- identifier、data ownership、保存期間、schema、migration、公開単位
- 権限、privacy、機密情報、課金、外部service
- 失敗境界、復旧、rollback、data lossの可能性
- interface、依存方向、交換可能性、複数機能を支えるinvariant
- 元へ戻しても、dataや当時の意図を回復しにくい判断

typo、意味を変えない文言やformat、既存の判断と外部挙動を保つ局所的なrefactorは`Skipped`にできる。省略するときも、「何を変えないため不要か」をStoryへ一行で残す。

迷ったときは、半年後に理由を失った状態で安全に変更できるかを考える。難しくなるなら`Required`である。

## Codexが先に説明すること

回答を求める前に、Codexが次を説明する。

1. 背景と、利用者に届く価値
2. 変更後も守るドメイン上のinvariant
3. 採用する案と、その判断軸
4. もっとも有力な却下案と、採用しない理由
5. 受け入れるrisk・不便・運用負担
6. まだ決まっていないこと

説明の粒度は利用者が判断できる高さに合わせる。class名やtable名が境界そのものでない限り、実装識別子を覚える負担へ変えない。関係が三つ以上に分岐するときだけ、小さな表や図を使う。

## 利用者へ尋ねること

質問は最大3問。そのStoryで荷重を支えるものだけを選ぶ。

- この変更は、利用者のどの価値やdataを守るものか。
- なぜ採用案を選び、別案の何を受け入れなかったのか。
- 失敗しても越えてはいけない境界と、戻せる部分はどこか。

場面を示し、「この場合に何を残すか」「二案のどちらを、何を基準に選ぶか」のように尋ねる。単なる二択、用語暗記、Codexの文章の復唱、「理解しましたか」「実装してよいですか」は使わない。

依頼文や直前の会話ですでに同じ内容が説明されていれば、その文章を回答として扱う。確認済みのことを聞き直さない。不足している判断だけを尋ねる。

## 判定と記録

| Status | 判定 | 次の操作 |
| --- | --- | --- |
| `Required` | 自己説明が必要だが、まだ確認していない | 説明と質問を行う |
| `Passed` | 目的、判断軸、守る制約がStory / ADRと十分に一致した | RED testへ進む |
| `Skipped` | 意味、境界、外部挙動を変えない局所変更である | 理由を残してRED testへ進む |
| `Blocked` | 三問以内で重要なずれや未決事項を解消できない | 実装を止め、Story / ADRを更新する |

`Passed`または`Skipped`になるまでRED testを始めない。回答に用語の違いがあっても、利用場面、trade-off、失敗境界が一致していれば不合格にしない。反対に、正しい用語を言えても判断理由を取り違えていれば`Passed`にしない。

回答を受けたCodexは、合っている点とずれた点を根拠付きで返す。修正後もずれが残り、三問を使い切った場合は`Blocked`とする。質問を小分けにして上限を迂回しない。

## Storyへの記録形式

新しいStoryは[Story template](../templates/story.md)から始め、次を短く埋める。

```markdown
## Understanding Gate（実装前理解確認）

- Status: `Required | Passed | Skipped | Blocked`
- Reason: なぜ必要か、または何を変えないため省略できるか
- Questions: 問うた判断。省略時は「なし」
- User explanation: 判断に必要な回答の要約。会話全文は保存しない
- Misalignment / Resolution: 見つかったずれと解消内容。なければ「なし」
- Unresolved: 残る未確定点。なければ「なし」
```

依頼文を回答として使った場合は、`User explanation`へ判断の要約を残す。個人情報、音源path、credential、会話全文は記録しない。

## 例

ファイル選択を「以前のLibraryへ追加する」仕様へ変える場合、Libraryの意味と保存集合が変わる。`Required`である。Codexは置換と追記の違い、再起動時に復元する集合、過去のMarkerやNoteへの影響を説明する。利用者には、再選択後に何が現在のLibraryとして残るべきか、その理由を尋ねる。

buttonの句読点だけを直し、accessible name、操作、layoutを変えない場合は`Skipped`にできる。Storyには「外部挙動と用語の意味を変えない文言修正」と残す。定型質問は行わない。

依頼文が「音源はコピーせず、選択したfileだけを置き換え、Markerとのidentityは再選択後も守りたい」と説明しているなら、その三点はすでに回答である。不足がなければ同じ質問を繰り返さず`Passed`にする。
