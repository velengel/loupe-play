# ADR 0004: 基盤画面では主操作と状態を先に見せる

## Status

Accepted

## Context（背景）

最初の画面は LoupePlay の考え方を伝える Hero と紹介カードを先に置いていた。その後へ音楽フォルダの選択を置くと、既定の 1180 × 760 ウィンドウでも主操作まで長くスクロールする。320px 幅では距離がさらに伸びる。基盤段階で確かめたいのは、完成像の説明より、ローカルフォルダを選び、音源を読み込めるという境界である。

もう一つ、音源を選んだ後の読み込み状態は native audio controls へ任せきりだった。長い一覧ではプレイヤーが残りの曲より後ろに現れ、キーボードで到達しにくい。codec や asset access が失敗しても、アプリの言葉では何も伝わらない。

## Decision（決定とその理由）

- デスクトップ基盤の操作領域を Hero の直後へ置き、概念を説明するカードは操作領域の後へ送る。操作領域でも音楽フォルダを SQLite health check より先に置き、狭い画面で最初に成立性を試せる順序へ合わせる。
- 曲を選ぶボタンは再生を開始したように見せず、「選択」と表記する。選択中は文字、背景、枠、`aria-pressed` を併用し、色だけに頼らない。
- 選択した音源の player は曲一覧より前へ表示し、明示的な選択の直後に player へ focus を移す。曲数が増えても、残りすべてを Tab で越えずに再生操作へ入れるようにする。
- audio の読み込み中、再生準備完了、失敗をアプリ側の state として持つ。`canplay` と `error` を live region へ反映し、失敗時には同じ音源を再読み込みできる操作を置く。
- 選択中の同じ曲をもう一度押した場合も、明示的な再読み込みとして扱う。表示だけを読み込み中へ戻さない。
- フォルダの選択・走査中は結果領域だけへ `aria-busy` を付け、その外に常設した live status で進行と検出件数を表示する。走査失敗も自動テストの対象にする。
- scroll container 内の曲ボタンには内向きの focus ring を使う。native controls には dark color scheme を伝える。

## Rejected Options（却下した選択肢）

- 紹介カードを先に残す: プロダクトの意図は伝わるが、基盤の主操作を探す負担が残る。
- 曲ボタンの click だけで `play()` を呼ぶ: 「選ぶ」と「鳴らす」を同時にし、音が出るタイミングを利用者が native controls で確認できなくなる。自動再生制約や codec failure の切り分けも難しい。
- player を一覧の後ろへ残す: 見た目の流れは単純だが、大きなライブラリほどキーボード操作の距離が伸びる。
- native audio controls の表示だけを状態通知とみなす: OS WebView ごとの差を利用者へ説明できず、失敗時の次の行動も示せない。
- focus を選択した曲ボタンへ残す: 一覧の比較には向くが、今回の明示操作は再生確認へ進む意図が強い。将来、矢印キーで移動する listbox を作る場合は別の Story で再判断する。

## Consequences（結果）

- 基盤の成立性を試す操作へ早く到達でき、読み込み失敗も LoupePlay の画面内で分かる。
- 曲を選ぶたびに focus が player へ移る。続けて複数曲を比較する操作では戻る手間が増えるため、ライブラリ操作を本実装するときに roving tabindex や専用 player layout を再検討する。
- `canplay` は再生開始そのものを証明しない。WAV、MP3、FLAC の decode、音、seek は Windows WebView2 を含む実機検証が引き続き必要である。
- native audio controls の幅や内部レイアウトは WebView に依存する。320px での視覚確認が得られるまでは、操作性を `UNVERIFIED` として扱う。
